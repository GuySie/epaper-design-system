# E-paper design system — working notes for Claude

Read this before changing anything. `work/` holds local working notes and is not in the repository: where it exists, also read `work/plan.md` (open work) and the end of `work/decisions.md` (latest decisions), and keep both up to date as the steps below say; where it doesn't, skip those steps or start the two files.

## Ground rules

- **Don't invent words.** Use the vocabulary in `docs/design-system.md` (*Vocabulary* and the *Glossary*). A new term needs the user's agreement first, then goes into `src/registry.yaml` (`terms`) so the glossary and the lint know it.
- **Example texts in rule text are English** (`NOW 19 ct`, `NO PRICES`), in the document and in a proposal, also when the mock-up or render they come from is in another language.
- Markdown: no hard wraps for readability on mobile.
- Metric units as default. Imperial for screen sizes only. 
- Don't over-explain; deliver, then say in a few lines what changed.
- Not affiliated with OpenDisplay: the system is the *E-paper design system*; "OpenDisplay" only names the integration the blueprints need.
- No upstream requests (issues or PRs to other projects) unless the user asks.
- Ask before deciding anything listed under *Open items* in the design system.
- **Values are generated, never typed; rule text is typed once, in its home.**
  - **Every token and every value is generated** and never changed by hand: tokens from the panel facts and the fitters (`lib/gen_tokens.py`); any value in `docs/design-system.md` that also lives somewhere else (code, tokens, metrics, input defaults, the registry) or follows from other values comes from that source through `lib/registry.py write`: a table between `registry` markers, a value in running text between `v:` markers (`lib/doc_values.py` lists what a `v:` marker can read). To change one, change its source or generator and regenerate; never type it into the document, a token file or a comment, not even a value a tool just printed. A new table of values gets a generator before it goes into the document.
  - **Rule text is typed, once.** Where the document is the only statement of a rule (the vocabulary, the token kinds, severity, states, the hero group versions, the rule columns of the token and component tables), it is written in the document, in one home, and the code follows it.
  - **A typed table or sentence never repeats a value or a rule that has another home**: it refers to it (*Section*, a token name). A table that mixes both keeps its rule words typed and gets its values generated.
  - **A list of pages is a value.** A sentence or table that says which pages have something (a stale state, thresholds, a footer, a pattern version) is generated from the page definitions and the registry (`v:stalePages`, `v:noStalePages`, `v:noThresholdPages`, `v:uses:<pattern>`), and the *Thresholds* and *Footer* tables are generated whole from each page definition's `thresholds` and `footer` (a layout may give its own `footer`; a layout without one stops the build). A new page can then never be forgotten in one.
  - A value still typed by hand is a known gap to convert, not a precedent.

## How a change goes (always this order)

The design system is prescriptive: the document says what is drawn, the code follows it. So a design change is written down and agreed **before** any code: first the rule text, then a mock-up of it (step 4, no release), and only then the build. Nothing is shown to the user as a *result* before it passes the checks; a mock-up is always labelled as one. Skipping ahead (code or a mock-up before the rule text, building before the mock-up is agreed, sizes picked by hand, the document "later") is the failure this section exists to prevent.

1. **Classify the change.** Refactor (no pixels change) · new screen (tier) · new layout of an existing page on a screen · new page · new or changed pattern version, module, component or token · text only. Say which, in one line, before starting.
2. **Read what the design system already says** about everything the change touches: the pattern and its versions, the modules and components it uses, the screen's tier, *Open items*, *To verify on hardware*. Note any rule the change would break or extend. **Then look at the current renders** of everything the change extends or reuses (`src/baseline/<reference>/*.png`, or `harness.py`): a flaw already drawn there (a cut label, a crowded cell) is part of the change and goes into the proposal.
3. **Design in the document first** (`docs/design-system.md`), for anything that isn't a refactor or text only:
   - New screen: derive its tokens (`python3 lib/derive_tokens.py W H Wmm Hmm`, canvas after rotation). Equal tokens = existing tier; otherwise a new tier key. *Same pixels, same spec*: a new layout reuses a spec when the canvas exists; a new shape needs a spec of its own.
   - New layout or new pattern version: write the rule into the pattern's section (what goes where, what gives way and in which order, centring, which tokens), in the existing vocabulary. Where the document already has a rule for the case (e.g. portrait screens), follow it or propose changing it explicitly.
   - New term: ask the user, then add it to `registry.yaml` `terms`.
   - **Name the worst-case values the rule assumes** (the longest text, the largest count, the widest reading) in the rule text itself: column widths and fitted tokens follow them, so they're design, not implementation.
   - **Measured tokens are per layout.** A layout's hero and strip icons are fitted on its own cases (`lib/layout_fit.py` `FIT`, `STRIP`, `GLANCE`), so a change to one page never refits another's. Say which of the layout's own measured tokens the change can move.
   - **One home per rule.** A rule is written once, in its section; elsewhere the document refers to it (*Section*, rule n) and never restates it, so two places can't drift apart. Search the document for the rule's key words to find every place that already states it, and turn those into references.
   - **Check the proposed rule against every existing rule it touches before showing it**, and say which ones: above all *nothing moves between states* (a warning, an alert or a chip appearing never shifts a line or the hero: `check.py` `SAME`), the gap rules (`C`, M, hero ÷ 7) for **every** state, not only the widest reading, and what gives way. A rule that only holds for the normal state isn't ready to show.
   - **An exception goes into the general rule's home.** Search every section the change touches for universal wording (`every`, `never`, `always`, `only`, `at most`, `the one exception`). Where the change breaks one, change that sentence in the same change and let the page's section refer to it; an exception written only in a page's section is how the document starts contradicting itself.
   - **Every rule sentence names its case.** For each new or changed rule sentence, the proposal names the check case (an existing one or one to add in step 7) whose render or check would differ if the code ignored the sentence: the uneven count for *two columns of equal length*, the black/white panel with both thresholds for the paper notch. A sentence no case can prove is labelled a proposal in the document, not written as a rule.
   - **Show the user the rule text and get agreement before writing code.** An *Open items* question is always the user's call.
4. **Mock it up and agree on it, without a release**, for anything that changes what is drawn (a new blueprint, layout, page or pattern version, or a changed one). Draw the agreed rule as a draft layout in a scratch folder (never `src/specs/`) and render it with `lib/preview.py` (the real macros and tokens, a new screen's tokens derived on the fly, measured tokens from a quick fit on that layout alone and marked as provisional), with the scenarios that matter (normal, the widest reading, warning, an alert). Show the renders labelled "mock-up, not checked", change the rule text and the draft together as the user asks, and repeat until the user agrees the mock-up looks right. No reference, no check cases, no tokens written, nothing in `src/` that a release builds from, and no release run during this step. The agreed mock-up and rule text are what the build must reproduce.
5. **Make a reference first** (before any code change, and only after the mock-up is agreed): a clean `EP_SAVE=<name> ./release.sh`, which keeps that release's renders and blueprint data as the reference `<name>`.
6. **Build it in `src/` only**, following the agreed rule and mock-up. While building, check only the affected layouts (their cases with `check.py` and `EP_KEYS=... lib/baseline.py cmp`) and run the cheap checks (registry lint, coverage lint) before any full release; run the full release once, at the end (step 8):
   - **Reuse the macros; never copy them.** A new layout draws with the existing component, module and pattern macros (`ds_macros.jinja`) and the shared spec pieces (`specs/_wx.py`, `specs/_cal.py`). When a macro doesn't fit as it is (it fills the whole screen, it has no bound, it reads one page's variables), change the macro so both uses share it (a parameter, a split into a module macro and its pattern, a shared spec piece) and prove the existing renders unchanged; never paste its body into a spec, not even in a mock-up that gets built. A copy is a second home for the same rule: when the rule changes, the copy keeps the old one.
   - Geometry comes from tokens, never literals. **Tokens are generated, never written:** no token value is typed into any file, not even one a tool just printed. Derived and floor tokens come from the panel facts (`lib/derive_tokens.py`); measured tokens (`type.heroShared`, `type.heroAlone`, the hero icons, strip icons) from the fitters (`lib/layout_fit.py`, the Hero group rule in `lib/hero_metrics.py`); `lib/gen_tokens.py` writes them all into `lib/ep_tokens.jinja` (`EP_TIER`) at the start of every release. If a token can't be generated yet, stop and say so instead of filling it in.
   - A new layout is one entry in its page's `layouts` (`src/pages/<page>.yaml`: its screen and `spec`) and its spec in `src/specs/<page>_<screen>.py`. Its key is page + screen (`weather_27l`); the build's keys and names, the check's blueprint map and canvas sizes, a file's screen and the registry's blueprints all follow from the page definitions (`lib/layouts.py`), so nothing else lists it. A new page also: its entry in `registry.yaml` `pages` (`name`, `uses`, `status`, the screens it isn't offered on, `widest`), its page definition (inputs in the scheme's order, data, texts in all eight languages, its rows of the *Thresholds* table in `thresholds`, and what its footer says, or `none` and why, in `footer`: the document's two tables are generated from them), and its section under *Pages* in the document (**Shows**, **Tested with**). A new pattern or pattern version also: its entry in `registry.yaml` `patterns` (`status: mock` until a page is built with it, then `live`), its macro in `ds_macros.jinja`, the macros of any new component or module in the registry's `components` and `modules`, and its section under *Patterns*. A new screen also: `registry.yaml` (`screens`, `screen_names`) and `pages/_shared.yaml` (`screens`, `screen_facts`). A new tier also: its panel facts in `lib/derive_tokens.py` `KNOWN` and its screen in `SCREEN_OF` there (plus `ALSO` for what else is known about its panels); the tokens and every tier table in the document are generated from them, and the screen's name comes from `registry.yaml` `screen_names`.
7. **Give it check cases**: scenarios in `src/scen/` for every kind of state in `lib/coverage.py` (`KINDS`, and `WX_KINDS` for weather; the widest reading is the one the rule text names, such as -12° with the moon; a grayscale panel is a case on every screen), the layout's row in `lib/coverage.py` (a case per kind, `n/a: <why>`, or `GAP` only with the user's agreement), then the cases in `lib/pixcmp_cases.py` (`CASES`, and for a weather layout `EXTRA_KEYS` and `_RULES`: the one list of cases, keyed by layout; `check.py`, `lib/baseline.py` and `lib/coverage.py` read it, and `check.py` derives from the registry which layouts must keep their hero, or their chart's frame, between states) a picture case `pic_<key>` (the coverage lint asks for one: the README's picture), for a page for any entities its `examples` in the page definition, and the fitter tables in `lib/layout_fit.py`, by layout (`FIT`: the widest readings of its hero beside other content; `STRIP`: layouts with strips; `GLANCE`: a Glance layout's ordinary reading).
8. **Read the diff as rule text, then run every check.** Before the full release, read the diff of `ds_macros.jinja`, the specs and the page definitions: every behaviour in it has its sentence in the document, and the cases step 3 named exist. Anything decided while building (a weight, a gap, a fallback, an order) becomes rule text the user has seen, or is undone; a code comment is never a rule's only home. Then run every check (see *Checks*), with one full release against the reference; this run is the release of step 11 unless the documentation of step 10 changes what is built: two identical builds, both lints, the coverage lint, `check.py` all cases pass, `gen_tokens.py` fits every measured token, `registry.py write` + `lint` 0 problems, and `baseline.py cmp` against the reference: 0 differences, or differences only in the layouts the change is meant to alter, named in `EP_EXPECT` (say which, and why). `./release.sh <reference>` runs all of these.
9. **Show the user the result** from the passing build (renders via `harness.py`), with what changed and anything that needs verifying on hardware. For a new or changed blueprint, also the text a user reads: its description and the labels and help of its inputs, as built for each screen (a count, a default or a part the screen doesn't have must be true on that screen).
10. **Finish the documentation**: the pattern text, the tables (`registry.py write`, which also writes the `README.md` blueprint table from the built blueprints), *To verify on hardware* for anything not yet proven on a device, an entry in `work/decisions.md`, and the finished item deleted from `work/plan.md`. After editing the document, run the registry `write` and `lint` again.
11. **Release** (see *Releases*).

## How the repo works

- `blueprints/` and `custom_templates/` are **generated**. Never edit them; change `src/` and run `src/release.sh`.
- A blueprint = its page definition (`src/pages/<page>.yaml`) + the layout for its screen (`src/specs/<layout>.py`) + the shared parts (`src/pages/_shared.yaml`, `src/lib/shared.py`). `src/lib/generate.py` writes it. The whole build is one command, `src/lib/build.py OUT [KEYS]`, which the release, the token fit and the mock-up tool all use.
- What several page definitions share is written once, as a group in `src/pages/_shared.yaml` (`groups`: the weather inputs and thresholds, the calendar texts, a few data templates). A page names it with `include: <group>`, as an item of a list or a key of a mapping. Numbered inputs (Plant moisture's 22 plants, Entities' 12) are written once as a list item `repeat: {from, to, items}`, with `{n}` for the number. Every tool reads the page definitions through `src/lib/pages.py`, which resolves the groups and stops on a key a page definition doesn't have.
- The macro files come from `src/ds_macros.jinja` (drawing kit, pattern macros), `src/lib/ep_tokens.jinja` (tokens per screen tier), the specs, `src/wx_steps.yaml`/`src/wx_txt.yaml` (weather), and the page texts. `src/lib/build_lib.py` writes them.
- `src/registry.yaml` is the index of patterns, pages, components, modules and terms. `python3 lib/registry.py write ../docs/design-system.md build` regenerates the tables between `registry` markers in the design system; `... lint ...` must report 0 problems.
- `docs/design-system.md` is edited directly, except its values: those are generated (see *Ground rules*).
- What each layout reads from its blueprint is derived, never listed: its tier from its page's screen (`derive_tokens.SCREEN_OF`), its inputs and the computed variables it is passed from the generator (`lib/build_lib.py`); the panel colour template is `src/ink.jinja`.

## Checks (all must pass before a release)

From `src/` with the project's `.venv` on the PATH (`export PATH="$PWD/../.venv/bin:$PATH"`; it holds `requirements.txt`), the fonts in `src/fonts/` (the seven TRMNL/Space Grotesk files from the README plus `materialdesignicons-webfont.ttf` copied from the installed `odl-renderer` package), and FriBiDi installed (`brew install fribidi`): without it Pillow has no Raqm, kerning isn't applied, and renders come out up to 1 px wider than the devices draw them. `python3 -c "from PIL import features; print(features.check('raqm'))"` must print True.

- `./release.sh [REFERENCE]` runs, in this order (it ignores a leftover `EP_KEYS`): the vocabulary rewrite of the code comments (`lib/vocab_apply.py code`, which edits the sources in place), the tier tokens (`lib/gen_tokens.py`: derived from the panel facts, measured ones fitted by `lib/layout_fit.py`), two builds that must be identical, `lib/shared.py --lint`, `lib/inputs_std.py --lint`, `lib/unread.py` (no input, text key or data key that nothing reads), `lib/coverage.py` (every layout has a case for every kind of state; it lists the remaining `GAP`s), `lib/registry.py check`, `check.py` (every case, pixel rules; it prints the failing cases and state differences), with a reference `lib/baseline.py cmp`, then `lib/registry.py write` and `lint` on the design system (its generated tables and values follow the build; 0 problems), and only then writes `../blueprints` and `../custom_templates`. A render needs Raqm: the harness stops without it.
- **Reference renders** are not in git (`src/baseline/` is ignored). `EP_SAVE=<name> ./release.sh` keeps a passing release as the reference `<name>` (renders and blueprint data, `lib/golden.py`); `./release.sh <name>` then proves a refactor draws the same pixels. The comparison lists `DIFF` (a render or payload differs), `NEW` (a case the reference doesn't have: listed, never a failure) and `GONE` (a reference render whose case no longer exists), and keeps the renders that differ or are new in `src/baseline/<name>.new/`.
- **An intended visual change** names the layouts it is meant to alter: `EP_EXPECT=key,... ./release.sh <name>`. Their differences are listed as expected; a difference in any other layout still stops the release. Log it in `work/decisions.md` and save the reference again.
- **While building**, check only the affected layouts: `EP_KEYS=key,... EP_CT=build/custom_templates python3 check.py build` and `EP_KEYS=key,... python3 lib/baseline.py cmp build <name>`. A key that is no layout stops the run.
- `python3 lib/golden.py save build <name>` / `cmp` compares blueprints as data (inputs, body) when a change must not alter behaviour.
- After a design-system edit without a release: `python3 lib/registry.py write ../docs/design-system.md build` and `... lint ...`.
- A release prints how long each step takes: about a minute when no layout needs fitting, about three minutes when all do. The check renders in parallel (one process per core, `EP_JOBS` limits it) and the reference comparison reuses its renders. Compiled templates are kept between renders (`EP_NOCACHE=1` compiles every time). The token fit is remembered per layout (`lib/ep_tokens.fit.json`: a hash of what the layout's fit reads, that is the shared sources, its drawing, its page definition, its cases and their scenarios, and the renderer versions), so a change to one page fits only that page's layouts; `EP_REFIT=1` fits them all. Run releases in the background.
- A one-off script that uses the check's parallel rendering needs `if __name__ == '__main__':` around its work: the worker processes import the script that started them.

## Releases

Each release: run `src/release.sh`, log it in `work/decisions.md` (what changed, renders identical or which ones changed and why), tag it only when the user asks, and tell the user whether the templates must be uploaded with the blueprints (always safest) and whether any automation needs migrating. Never trigger disabled automations; after the user uploads a release, offer to redraw the enabled ones.
