# Building and checking

How the blueprints and templates of the E-paper design system are built and checked. None of this is a design rule: the rules are in [design-system.md](design-system.md), and the names in *italics* here are its sections. The working rules for a change, and the commands, are in `CLAUDE.md`.

## Registry and reference renders

- **`registry.yaml`** lists the patterns (with their versions) and the pages; a page's layouts and blueprints come from its page definition (*Blueprint mechanics*, *Names and files*). The tables between `registry` markers in the design system are generated from it and from the blueprints' inputs (`lib/registry.py write`); change the registry, never those tables. `lib/registry.py lint` fails when a generated table was edited by hand, when the Components or Modules table disagrees with the registry's components and modules, when a code comment calls a module a component or the reverse, when a page or pattern name of more than one word is written in lowercase (ordinary uses are listed in `CAPS_OK`), when a glossary term is not used anywhere in the design system, when a cross-reference names no heading or named part, when a word is written twice in a row, and when a word the vocabulary rules out (`Grid`, `family`, `tag`, `variant`, …; the list is in `lib/vocab.py`) appears in the design system, in a code comment or in a blueprint.
- **Vocabulary in what we ship:** `lib/vocab.py` rewrites the blueprints' own texts and the code comments to this vocabulary (a Solum device is an ESL, every other one a device); `lib/vocab_apply.py` runs it on the code and on every package.
- **Reference renders:** every check case of every blueprint, rendered from a released package (`lib/baseline.py save`). A release that only reorganises code must render the same pixels (`lib/baseline.py cmp`, 0 differences).
- **Rules and code:** the words are the source. `lib/rules.py` reads the rules the code cites (`*Section*, Rule name` in a comment or a check's message): `lint` fails on a citation the document doesn't have and on a cited rule whose text changed unconfirmed, `accept` confirms, `trace` prints the table of rules and where they are implemented or checked.
- **Impact:** `lib/impact.py MACRO ...` (or `--diff [REF]`) lists the layouts and pages that draw with a macro, directly or through other macros: the pages to read again before a change to the kit, and to name in its result.
- **Tokens:** `lib/gen_tokens.py` writes the tier tokens at the start of every release: derived from the panel facts, and the measured ones fitted on a build (`lib/layout_fit.py`, see *Token register*, *Measured*).
- **Release:** `src/release.sh [REFERENCE]` builds the macro files from the sources and generates every blueprint from its page definition (`lib/generate.py`), then puts the inputs in the scheme's order and writes the shared parts. A second build must come out identical, and it writes `blueprints/` and `custom_templates/` only when every check passes: the shared parts, the input scheme, the pixel check and, with a reference, the reference renders. What each layout reads from its blueprint is derived by the build (`lib/build_lib.py`), never listed.
- **Page definitions:** the package is output only: a change goes into `pages/`, `specs/` or the shared parts, never into a blueprint. A blueprint is generated from its page definition, the layout for its screen and the shared parts (each shared part is written once, in `lib/shared.py`). One file per page, `pages/<page>.yaml`, next to the registry, which stays the index (name, pattern, status, versions per screen, widest reading). Its fields:
  - `description`: `shows` (one sentence), `works_with` (screens and panel colours, generated from the layouts), `needs` (the page's integrations; the OpenDisplay integration, the templates and the fonts are added for every page), `trigger_advice`, `notes` (per page and per layout) and `links` (repository, design system, fonts, integrations, generated). No sizes or design details: the design system holds them.
  - `inputs`: the page's own inputs in the input scheme, the main one `required: true`; the shared inputs come with the shared parts. Their help is made specific: the device input names the screen, the rotation gives the panel's native orientation and the upright value, the header title says what a blank title becomes (the page's title text, or `title_default` in the page or a layout), and the time format says which times (`times` in the description). The screens' sizes and native orientations are in `pages/_shared.yaml`.
  - `redraw`: `trigger` (the user picks the trigger, with the button flash), `change` (the page redraws when its entities change: Doors & windows) or `button` (its own button: Medication).
  - `stale`: the entities whose last report decides whether the data is stale; none for a page without a stale state.
  - `data`: the actions that fetch data, the computed variables, and when the error view is drawn. What the spec reads comes from the layout, never from a list.
  - `texts`: the page's strings per language and the shared day and month lists it uses.
  - `layouts`: per screen the spec and what differs on that screen (input defaults, constants, notes, `drop_inputs` for the inputs the screen doesn't offer, `shows_instead` where the page's `shows` sentence isn't true on that screen). In `shows`, `{n:<name>}` is the number of numbered inputs `<name>_<n>` the screen offers.
  - `thresholds`: the page's rows of the design system's *Thresholds* table: `data` (what is measured), and `what` (the values are the defaults of `warning_<what>` and `severe_<what>`, after `at`) or typed `warning` and `severe` words.
  - `footer`: what the page's footer says, or `none` and why; a layout may give its own. The *Footer* table is generated from it.
  - `examples`: for a page for any entities, the check cases shown as examples in the README and the design system.
  - Shared lists in `pages/_shared.yaml`: the links, each URL once, and the integrations (name, URL, and a minimum version only where it matters).
- **Frozen package:** `lib/golden.py` keeps a released package as data (inputs, description, triggers, conditions, variables and actions, formatting ignored), so a later package can be compared with it.
- **Decisions** and their reasons are logged in the working notes, outside the release.

## Ink placement and checking

- **Place ink, not boxes.** Every position in the design system is measured to the ink, so layouts place ink, not anchor points:
  - TRMNL text: caps and digits span `y − CAPUP` to `y + CAPDN` (4/3 at 12 px, 5/5 at 16, 7/7 at 21). `TOPY(top, s)` and `BOTY(bottom, s)` give the anchor for a wanted first or last ink row.
  - TRMNL advances end in 2 px of space; the `T` macro shifts right and centre anchors so the ink itself ends on (or centres on) x.
  - TRMNL glyphs also start 1 px right of their anchor (2 px at 21; the `LSB` table); the `T` macro shifts left anchors back so the ink itself starts on x. The title's first letter sits exactly on P.
  - The renderer kerns: pairs such as `1,` (−2 px) or `TE` (−1 px) draw closer than their advances. Widths include the `KRN` table (capitals, digits, number punctuation), or anything placed after a measured string lands too far right.
  - Space Grotesk numerals start a few px right of their anchor (side bearing per digit and size, measured for every rung of the hero ladder by `lib/hero_metrics.py`); `HERO_INK_X(x, text, size)` gives the x that puts the first digit's ink on x; `HERO_INK_W(text, size)` gives the string's ink width (measured, never estimated).
  - MDI icons have padding inside their box; place them by their drawing, not their box.
- **Every release is measured.** `check.py` renders each blueprint for each test scenario and measures every element's ink (descenders excluded at the bottom). It checks the title row (*Title row*: the title line's position, the title caps, the update stamp's end), the padding (*Physical size minimums*: all ink inside it, the lowest ink where a layout fills the screen), fills and warning outlines overhanging no further than a chip hangs (*Spacing (internal)*, *Chips hang outward*), where content starts (*Spacing (internal)*, *Content starts M below the title line*; Hero dashboard hero bands: the `C` rule, *Hero dashboard*), the hero clearance and the hero group's `space.l` gap, its moon badge included (*Hero group*), and no moon badge ring cutting a line (*When to use an icon*). It also checks that no text overlaps other text, an icon or a line; that nothing drawn later covers a hero numeral; that every fill stays on the canvas and text on a fill stays inside it; and that a page keeps its layout from one state to the next (*Pages*, Rules for every page: the hero size, the lines, and on a Hero dashboard the hero icon; a chip may take a line's place). A build that fails is not packaged.
